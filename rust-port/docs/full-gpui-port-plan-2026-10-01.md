# Full GPUI port: implementation and acceptance plan

Date: 2026-10-01
POC: The checkout contains two synthetic GPUI experiments under `rust-port/`; neither reads production state. The documentation and reproducible prototype sources are collected on `feat/gpui-frontend-port`; build caches are excluded. This document is a plan, not evidence of a shipped port.
TL;DR: Build and prove a complete native frontend against the existing TypeScript business owners first. Only then move those owners out of Electron, replace platform services, migrate installed users and ship target-specific packages. Preserve the Chrome extension and browser-owned ChatGPT execution.

## 1. Target and non-negotiable boundaries

The finished product has a Rust/GPUI workspace, a supervised local TypeScript host for existing session/input/Goal/agents/MCP/bridge/plugin ownership, and the companion Chrome extension. No production feature may silently disappear; any deliberate scope change requires a user-approved exception in the coverage ledger. Electron is retained until frontend parity has been demonstrated; a Rust rewrite of the business backend is a separate proposal, not a hidden step in this port. The existing [frontend inventory](gpui-frontend-port-plan.md#complete-frontend-coverage), both preload allowlists, and [AGENTS.md](../../AGENTS.md) define the starting behavioral contract; current source and observed behavior must be checked again when each slice begins.

One fact has one owner. GPUI may own focus, selection, draft presentation, viewport and local preferences; it does not decide whether a message was accepted, delivered or completed, whether a tool may run, which conversation owns a worker, or which paths/credentials are allowed. Unknown identity fails closed for mutations. A UI transport acknowledgement is not a ChatGPT Send receipt. Native GPUI and the old Electron workspace must not become independent writers to the same userData. During comparison, elect one interactive writer and keep the other read-only or use isolated userData.

The initial host is Electron main with narrow adapters. The final host is a standalone, supervised Node process preserving the same TS owners; Rust provides only named OS services where needed. The extension and its protocol remain unchanged unless a concrete integration contract requires a versioned change. Source, tests, build, package, installed bytes and signed-in/live device behavior are separate evidence levels. Each stage below has an exit gate; code complete without its gate is still in progress.

## 2. Framework research and pinned implementation rules

The [GPUI project site](https://gpui.rs/) is the discovery entry point. Use the exact revision declared in each crate's `Cargo.toml` and `Cargo.lock` when implementing; `main` moves. GPUI is pre-1.0 with expected breaking changes; its README shows `gpui_platform::application().run(...)` for standalone startup. [1, lines 586-602] Record the Rust toolchain, Zed revision, enabled features, dependency/license review and target build prerequisites in every feasibility report. Upgrade GPUI only as a separate change with all platform and UI gates rerun.

- `App` owns entities; `Context<T>` adds entity-specific observation/event functions, while async contexts may outlive their windows and entity updates can fail. [2, lines 583-599] Give each view one presentation-state owner. Retain subscriptions/tasks with a named owner, drop them at disposal and recheck session/draft key, selection generation and backend incarnation after each await, including A → B → A.
- Observations can be retained or detached; dropping a retained subscription cancels it. [3, lines 997-1001] Detach only for deliberate app-lifetime work. Never let an inactive panel retain a transport stream. Keep render pure: parse, decode and fetch outside `Render`, then publish only after an owner check.
- The official key-dispatch guide uses typed actions, `on_action` and scoped `key_context` bindings. [4, lines 613-670] Point menu, mouse and keyboard at the same validated action. Composer, transcript, sidebar, modal and terminal contexts must not steal one another's keys.
- `EntityInputHandler` integrates through `ElementInputHandler` and `Window::handle_input` during paint, with selected text represented using UTF-16. [5, lines 1111-1153] Implement UTF-8/UTF-16 boundary mapping, selection and marked-text replacement explicitly. The example converts pasted newlines to spaces; [6, lines 1345-1351] do not use that single-line behavior for the composer. Prove IME, undo and multiline behavior on real OSes before choosing the editor.
- A `List` needs notification via `splice` or `reset` when offscreen heights change. [7, lines 1116-1122] Keep canonical row ID outside list index; test anchor identity and pixel position across prepend, late image sizes, folds, width changes and streaming. Tail follow applies when the reader is at the bottom; [7, lines 1312-1328] it must not drag an off-tail reader. The small [official list example](https://github.com/zed-industries/zed/blob/66432e4ca957383dcc9ec61d1353a4b4bd94c6bc/crates/gpui/examples/list_example.rs) measures all its rows; do not scale that incidental choice to a 10,000-row transcript.
- AccessKit nodes need unique global IDs and roles to be reported; [9, lines 1195-1217] repeated text from one source location can collide across rows. [9, lines 1355-1405] Derive repeated view identity from stable session/message/input IDs, handle accessible actions and verify screen-reader focus/reading order on devices.
- The pinned test module supports `#[gpui::test]` and `TestAppContext` with deterministic test executors. [10, lines 971-1017] The current prototype additionally needs GPUI's `test-support` dev feature. Test logical state, painted GPUI behavior and real OS behavior separately.
- The pinned README documents Metal and `font-kit` on macOS, Wayland/X11 features on Linux, Win32/DirectWrite on Windows and Xcode tooling for Mac builds. [1, lines 611-657] Feature declarations are not cross-platform acceptance. Evaluate maintained components for multiline editing, selectable Markdown, highlighting/diff, terminal emulation and PDF rendering by pinned API, license, accessibility and platform evidence; do not assume Zed's higher-level UI crates share GPUI's license.

## 3. Work tracking and repeatable slice procedure

Use [the existing start plan](implementation-start-plan-2026-10-01.md) for the immediate M0 sequence and [the detailed frontend plan](gpui-frontend-port-plan.md) for screen-level coverage. Use the initial [coverage ledger](coverage-ledger.tsv), [source inventory](source-inventory.tsv), [execution guide](execution-guide.md) and [ordered task cards](task-cards.md). All initial ledger rows are planned and require owner mapping before production integration. Keep one **coverage ledger** under `rust-port/docs/` before production integration. Each row needs: source module/control/preload operation or subscription; product invariant and authoritative TS owner; GPUI view/action; local state lifetime; transport operation and response/error semantics; identity/epoch fence; milestone and status (planned, implemented, tested, accepted or explicitly deferred); positive/negative fixture; keyboard/a11y/locale check; native platform and package evidence; reviewer. Subrows represent independently reachable menus, dialogs and actions. Re-enumerate both preload allowlists and renderer modules/assets when the app changes; do not rely on the old 123/14 and 8/4 counts. Do not mark a group accepted if any subrow is missing.

Every slice follows: (1) inspect current source, owner chain, status and diff in this shared tree; (2) name the first wrong boundary or required invariant and consider an alternative; (3) implement a narrowly owned feature and adjacent negative test; (4) exercise GPUI state, real rendered UI, TS owner suites and live provider where relevant; (5) check bounded memory and disposal; (6) update ledger, worklog and user-facing instructions with commands/results/gaps. Do not reset or overwrite another contributor's dirty work. A user-visible disabled placeholder is acceptable only in internal builds and must remain open in the ledger. Keep private userData/recordings and credentials out of fixtures and docs.

## 4. Milestone gates and step-by-step build order

### M0: decide whether GPUI can support this product

1. Consolidate the two experiments by choosing `rust-port/gpui-prototype` as the variable-height list baseline. Keep the other crate for comparison until its shell/accessibility/file-drop lessons are either integrated and tested or deliberately retired. Preserve historical files when moving them; never mix fixture and production authority.
2. Add synthetic append and controlled streaming; test bottom follow and the negative scrolled-away case. Draw before/after prepend with the same visible row and intra-row offset; exercise eviction, changed text wrapping, delayed image dimensions, disclosure open/close, viewport resize and long Markdown/code. Test empty and very large rows. Avoid whole-list `measure_all()` in the large workload unless measured evidence justifies a bounded variant.
3. Build a real multiline composer through the pinned native input-handler path. Cover selection, clipboard, undo/redo, grapheme and UTF-16 boundaries, RTL, emoji, marked text, candidate positioning, Japanese/Chinese composition, Enter during composition, Shift+Enter, paste/drop and disabled/read-only state. Decide cross-row transcript copy/selection before production history; if virtualization blocks it, test and document another renderer/selection strategy.
4. Exercise typed key actions and focus traversal; add stable accessible row/control identities and inspect the resulting accessibility tree and spoken order. Add representative resizable docks, theme/contrast/text-scale/reduced-motion, synthetic file drop, modal focus and narrow-window behavior.
5. Establish a same-hardware 10,000-row Electron comparison with equivalent streaming/image/code workloads. Record startup, scroll-frame latency, input response, memory, GPU footprint where observable, idle CPU/wakes and recovery from hide/show. Set budgets from measurements, then check Linux Wayland and X11 and representative Windows/macOS builds, IME, accessibility and rendering on intended architectures.

**Gate M0:** produce a feasibility report with exact toolchain/pin, commands, OS/GPU/display, numbers, screenshots or test traces, failures, editor/selection/component decisions and unresolved scope. A test that reads `logical_scroll_top()` does not prove painted anchoring; a five-second process smoke does not prove input, selection or a11y. No production transport until M0's input/selection/platform decisions have evidence or an explicitly approved scope change. If a framework blocker is found, keep Electron and assess alternatives before accumulating integration code.

### M1: native read-only workspace with Electron-hosted TS owners

1. Draw the minimal operations from `src/main/ipc.ts`, `src/main/session/read-model.ts` and the two preload inventories. Start with state/connection, project and session catalog, selected session detail and paged history, then activity invalidation and read-only worker drawer. Share the original owner functions; do not copy business logic or extract the whole IPC layer first.
2. Supervise a Rust child from the existing backend in an explicit development mode. Prototype private inherited pipes with length-prefixed bounded frames, fixed named operations, version/incarnation handshake and peer lifetime; if sockets are required, use OS-local access controls and authentication. No generic IPC bridge, privileged renderer channel, credential read, or production userData write by GPUI.
3. Define versioned schemas and matching TS/Rust fixtures: request ID, session/turn/input owner, response and error codes, selection/load generation, subscription sequence, canonical `position` versus revision `seq`, max bytes/decoded pixels, deadlines and cancellation. Start each subscription at a snapshot boundary and reread on gaps. Limit queued updates and cache residency. Restart invalidates the old backend incarnation and all outstanding capabilities.
4. Implement catalog, transcript and worker read views. Retain inert painted content while selection loads, clear it on failure, and fence A → B → A late replies. Page by immutable origin, preserve off-tail viewport through live revisions, keep tool detail lazy, reconcile an input bubble only through exact outbox/history identity. Show disconnected/unavailable state without inventing completion.
5. Test serialization against malformed/oversized/truncated frames, duplicate and missing events, race/reconnect/disposal and stale A → B → A; run existing TS owner tests. Compare screenshot, keyboard, accessibility and responsive behavior with isolated Electron fixtures.

**Gate M1:** the same canonical read projections appear without duplicate ownership, stale overwrites, lost pages or unbounded buffers. Rust and TS fixture suites pass; no GPUI mutation surface exists yet. Electron remains the writing workspace.

### M2: one complete task interaction path

1. Implement separately keyed, window-local project and unfiled New Chat drafts. Repeated New Chat/navigation preserves text, attachments, prepared plan, objective/mode and delivery choice; manual deletion stays deleted. Async file import, model lookup and planning results carry draft key and replacement generation.
2. Project the account-observed model/effort catalog without inventing entitlement. Stage immutable originals through the existing input owner; keep opaque IDs, preview limits, upload versus tool-image paths and truthful missing/failed staging. Add typed Send and injection/after-turn/finish choices only after owner checks.
3. Call the existing outbox with stable input IDs. Render queued/admitted, composer-inserted, authorized, confirmed sent and uncertain as different states. Retry only when the outbox permits it; never replay an authorized ambiguous Send. Reconcile pending to canonical history once, even if the history row later leaves the resident page.
4. Add queue edit/reorder/cancel and immediate tool injection, ensuring claim races leave immutable claimed payloads. Add exact-chat Stop, finish release and Block as distinct controls. Implement generated workflow checkpoints, Goal/Loop decision/progress/recovery, worker communication, Compact & Resume and context estimates through their existing owners, retaining session/project/queue identity across A → B. A countdown or displayed `update_plan` grants no delivery or completion.
5. Exercise native Send on the real signed-in page and installed extension, including attachment upload, thinking failure, active-turn correction, late receipt, stop, cancellation, worker report and compaction. This validates product behavior; it does not authorize repeating uncertain work.

**Gate M2:** a user can start, steer, inspect and continue a task from GPUI without duplicate sends or cross-chat effects. Run TS outbox/bridge/continuation/Goal/agent suites, Rust transport/entity tests, painted native controls and signed-in browser cases. Failure/uncertain paths must be as visible and safe as successes.

### M3: all remaining frontend parity, in dependency order

1. **Shared foundations:** native icon/font/assets and license review, theme tokens, text scaling, contrast, reduced motion, English labels and all ten current locale catalogs; semantic controls, native dialogs/menus, keyboard actions, scoped focus and accessible feedback. Test locale switch mid-draft, dynamic errors/attributes, date/number formatting, CJK wrapping, Turkish case folding, RTL/authored/provider/path text unchanged, narrow layouts and screen readers.
2. **Setup/security presentation:** first-run guide and images, folder approval, profiles/tunnel/connection, extension pairing and diagnostics, rooted permissions/capabilities/read-only/command policy, privacy/recording settings, appearance and model/helper settings. Preserve three-way settings merge and secrets written only by the backend. Negative tests: stale settings save, permission revoked during work, hidden/unavailable controls, failed/cancelled picker and profile epoch race.
3. **Transcript and authoring detail:** safe Markdown and citations/links, images and placeholders, reactions, tool outcomes and nested detail, folding, copying/export, displayed agent plan, worker drawer/inbox, handoffs, completion unread state and history scroll. Validate huge output and delayed previews with bounded decode and no anchor drift. Keep tool arguments/results lazy until disclosure opens.
4. **Workspace:** right/bottom docks, project file tree/watchers, text/code editor and revision-checked save, Markdown/image/PDF preview, read-only Git Review versus recorded tool-edit review, PTY terminal tabs and output acknowledgement/backpressure. Negative tests: project switch during preview/save, symlink/revocation/refusal, revision conflict, binary/oversized asset, terminal flood/hidden exit and close while spawn is pending. Native dialogs need an explicit window/OS parent while Electron still hosts them.
5. **Integrations:** plugin catalog/install/OAuth and connector-refresh truth, skills library/completion, usage estimates versus provider limits, diagnostics/logs and redaction, updater/notices, browser preferences, pets/library and separate overlay with click-through/focus/multi-monitor behavior. Keep extension popup and injected UI as separate retained browser frontends; test their integration without treating them as GPUI screens.
6. **Preferences and migration:** inventory every `localStorage`/renderer value and transient owner: language, appearance, sidebar order/read receipts/width, docks/preview sizes, selected tabs/disclosures/scroll, draft and edit buffers, usage formula/week start, dismissed notices, pet layout. For each specify source key/version, storage lifetime, default/corrupt behavior, migration/import/rollback and native test. Never mirror permission, session history, send receipt, Goal debt or worker authority into UI preferences. UI reload and restart have different preservation requirements.

**Gate M3:** every reachable screen, dialog, operation, subscription and saved UI state in both preload surfaces has an implemented or explicitly user-approved disposition in the ledger. Feature-by-feature TS owner tests and GPUI logic, painted keyboard, a11y, localization, narrow/zoomed, reduced-motion and native-device tests pass. Repeat `npm run verify`, `npm run build`, and for renderer-side parity references `npm run verify:ui` on the unchanged Electron path. GPUI cannot be called a full frontend port while a terminal, editor, PDF, pet overlay, auth dialog or input status remains a placeholder.

### M4: retire Electron only after frontend parity

1. Map each remaining Electron dependency and caller: startup/single-instance lock, paths/resources, safeStorage, dialogs/file picker, clipboard, shell/open URL, notifications/tray, window/layout/overlay, OS consent, native Desktop helper, updates and quit. Keep TS business owners unchanged and replace each service with a narrow named adapter. No generic Rust RPC exposing filesystem/commands/secrets. Ensure one owner supervises GPUI and Node: backend crash, window close, startup race, reload, update and shutdown must not create two writers or leave tool work stranded.
2. Host TS services under a packaged, pinned Node runtime. Check Electron-specific API isolation before removal; rebuild and smoke native node-pty, Sharp, tree-sitter, Koffi and macOS helper against the actual runtime ABI on each target. Preserve accepted HTTP drain and durable flush order, timers/process teardown and bounded shutdown. Do not assume GPUI's short native quit grace can replace the backend's shutdown budget.
3. Migrate encrypted `secrets.bin`, profile-scoped keys and plugin OAuth storage using the old decryptor in a bounded one-time migration. Verify new encrypted storage before retiring old ciphertext; interruption, corrupt source, wrong OS user/keyring and restart must fail safely without plaintext temp/export files or insecure Linux fallback. Preserve permissions/config choices and existing session, outbox, project and worker ledgers without rewriting live data as a repair shortcut.
4. Preserve stable `userData/extension` mirroring, extension manifest/bridge-protocol/version alignment, pairing/revocation credentials, bridge port/auth rules, browser selection/recovery ownership and installed extension behavior. Native platform checks cover Windows capture/input helper, packaged macOS Screen Recording/Accessibility identity, Linux capability masking, multi-monitor/window focus and background browser behavior; an unsigned Mac smoke does not prove signed/notarized consent continuity.
5. Build Windows x64/arm64 NSIS, macOS x64/arm64 DMG and ZIP, Linux x64/arm64 AppImage and DEB. Preserve app identity, installed userData location, version synchronization, tunnel/rg binaries, extension payload, notices/native-source material, OS permissions, update checksums and safe staged-update handoff. Test clean install, upgrade from Electron with real-format **synthetic** data, crash mid-migration, restart, rollback constraints and uninstall/reinstall without losing data. Compare installed payload hashes to reviewed packages, not just version labels.
6. Update CI for all target builds, Rust + TS contracts, native ABI and package smoke. Keep the repository's privacy/public-history, third-party notices, native-source, SHA-256, signed/notarized where required and release-absent gates. Publish only from a reviewed version tag with release notes and inspect public artifacts. Keep original Electron updater available for the transition until verified GPUI upgrade adoption; define how existing users receive the new installer without trusting a label alone.

**Gate M4 / release:** zero unexplained Electron dependencies or unowned processes; security negative tests and data/credential migration pass; every supported artifact runs from installed bytes on its OS; permission, extension, browser/tool and updater flows are observed; CI and release integrity gates pass. Package/install/live proofs are recorded separately. A Rust rewrite of the TS backend is **not required** for this gate.

## 5. Cross-cutting regression and failure matrix

| Fault or race | Must remain true | Minimum proof |
| --- | --- | --- |
| A → B → A navigation; late worker/read/import reply | Old generation cannot repaint, attach or send into the returned A | Pause A before response, complete B, return to A, release A; Rust entity + transport test |
| Prepend, eviction, image height or disclosure update | Same visible canonical row/offset persists off-tail; following reader alone moves with tail | GPUI draw/scroll assertions plus native painted check |
| IME, pasted multiline text, emoji/RTL or focus change | No partial composition Send, broken UTF boundary or stolen draft focus | GPUI edit tests and real Windows/macOS/Linux input |
| Duplicate/lost transport ACK, restart or slow native Send | Owner's outbox receipt decides sent/uncertain; no blind resend or duplicate bubble | Rust/TS wire fixture, outbox integration and signed-in browser |
| Queue head claimed during edit/reorder; user Stop | Claimed bytes stay frozen; Stop is not cancellation or completion | Owner test + UI negative case |
| Historical final/interim/error arrives late | Only proven final closes correct turn; progress never grants completion/recovery | Store/bridge tests + transcript display |
| Profile, project, root or permission changes while loading | No stale permission grant, wrong cwd or cross-family tab/process use | TS policy tests + GPUI stale-view/refusal |
| Disconnect during subscription/action; backend reincarnates | Accepted work survives at owner; UI disables unsafe actions and rereads snapshots, never replays mutation | Transport fault injection and host restart |
| Text/image/PDF/diff/terminal flood or corrupt payload | Bounds at frame, decode, cache and rendering; original evidence retained or loss explicit | fuzz/size cases, memory benchmark and UI fallback |
| OAuth or credential migration failure | No plaintext leak, lost working secret or broader access | migration interruption/negative tests + installed upgrade |
| OS permission denial, native modal or minimized window | Honest unavailable state, recoverable focus and no false action success | real platform manual automation checklist |
| UI close while tool/bridge work continues | Backend drains or retains accepted work by its existing owner; no orphan writer | process lifecycle and shutdown integration |

For every checkpoint run the smallest relevant Rust and TS suites, then the wider repository gates when production owners/protocols change. Keep a tested failure reproduction when a platform gate cannot yet run; missing target hardware is an open gate, not a pass. Track test coverage by behavior and owner rather than by number of tests.

## 6. Validation cadence, rollout and rollback

At each prototype slice run `cargo +stable fmt --check`, `cargo test --locked -j 1`, `cargo check --locked -j 1` and `cargo build --locked -j 1` inside the selected crate. Keep a fixed synthetic corpus with empty/long messages, public interim/final revisions, image load failures, large code/tool rows, foreign agent rows and both followed/off-tail scroll positions. Run a native UI interaction check for the affected feature on the current OS, noting that the other target OSes remain unverified until exercised there. When a named TS owner or wire contract changes, run its nearest `test/*.test.ts` suites and both ends of the protocol. Before claiming production frontend parity run `npm run verify`, `npm run build` and `npm run verify:ui` on the Electron comparison build, alongside the Rust test and platform matrix. These commands do not substitute for real browser, native device, or installed-package checks.

Review checkpoints are M0 framework go/no-go, M1 read-only integration, M2 trustworthy task interaction, M3 complete frontend parity, and M4 host/installer migration. At each checkpoint file an evidence report containing the exact commit or dirty-tree snapshot, version pins, command and environment, measured result, reproduction for failures, coverage-ledger delta, known deferrals and an explicit reviewer decision. Set numerical performance budgets only after recording the equivalent Electron workload on the same machine; regressions in memory, startup, scroll or idle should remain open until explained or explicitly accepted. Keep the existing Electron application usable as the fallback throughout M0–M3.

Ship a candidate first to isolated profiles with synthetic and consenting test data, then a limited opt-in installed-user cohort; compare crash/launch failure, retained session/outbox integrity, memory and CPU, accessibility and native input, bridge connectivity, send receipts and tool outcomes against the Electron baseline. Do not automatically retry ambiguous inputs as a recovery technique. Gate broad rollout on the target matrix and incident triage rather than elapsed time. The rollback path must launch the previous app without deleting or downgrading its encrypted store or userData; migration should preserve old ciphertext until new storage is verified, and tests must establish whether an older app can still open the data after migration. If compatibility cannot be guaranteed, stop before automatic upgrade and provide a tested backup/recovery route that never exports plaintext secrets. Keep a versioned compatibility/migration record and a deliberate cutoff for retiring the Electron fallback only after adoption and installed-runtime evidence.
